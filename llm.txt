# Tempest LLM Guide

Tempest is a YAML-based HTTP API test runner. It recursively discovers test-project files, sends HTTP requests, evaluates response assertions and saved-variable expressions with CEL, and renders output with Liquid report templates.

Use this file when helping someone write Tempest tests, configs, custom reporters, examples, documentation, or code changes. Describe only behavior implemented in the repository.

Keep these expression systems distinct:

- CEL is used for response assertions and for the expressions on the right-hand side of `vars:`.
- Liquid is used to interpolate spec inputs such as routes, headers, bodies, assertions, and options. It is also used for custom report templates.
- Parse JSON response content with `body.json()`. The old assertion variable `json` is obsolete and does not work.

## Quick Start

Minimal test file:

```yaml
# health.spec.yml
name: "Health check"
test:
  route: "https://httpbin.org/status/200"
  assert:
    - status == 200
```

Run with Docker from a directory containing test files:

```bash
docker run --rm -v "$PWD:/etc/tests" mattisthegreatest/tempest test
```

Run from this repository with Cargo:

```bash
cd tempest
cargo run -- test --path ../examples/tests --run pass
```

The full `examples/tests` tree intentionally contains passing, flaky, and failing tests and calls public network services. Use `--run pass` for a successful smoke run.

## CLI

Tempest currently has one subcommand:

```bash
tempest test \
  [--path ./path/to/project] \
  [--run ./relative/spec-or-directory] \
  [--debug] \
  [--retries 2] \
  [--workers 4] \
  [--strict] \
  [--warn-as-err]
```

CLI behavior:

- `--path` is the test-project root. It defaults to `/etc/tests` for Docker volume mounts.
- `--run` limits execution to one spec file or subdirectory beneath `--path`. It defaults to the whole project. is an array.
- `--debug` prints the resolved route, response status, response headers, and response body. It does not print outgoing request headers or the request body.
- `--retries N` sets the default number of additional attempts after an assertion failure.
- `--workers N` sets the maximum number of spec files in flight. Supplying it enables file concurrency; `--workers 1` forces serial execution.
- `--strict` makes an otherwise non-failing run containing flaky tests exit with code 2.
- `--warn-as-err` makes any collected warning cause exit code 1. `--warn-as-err` also has the short form `-w`.
- `--debug` and `--strict` have the short forms `-d` and `-s`.
- `--env` or `-e` is an array of base environment variables. Eg; `-e KEY1=value1 -e KEY2=value2`

## File Discovery

Tempest recursively scans the project selected by `--path`.

Recognized YAML files:

- `*.spec.yml` or `*.spec.yaml`: test descriptor trees.
- `*.config.yml` or `*.config.yaml`: cascading run options.
- `*.template.yml` or `*.template.yaml`: custom report templates.

File names matter. The YAML file stem must end with `.spec`, `.config`, or `.template`. For example, `users.spec.yml` is recognized, but `users.yml` is ignored.

Files whose names end in `.env` provide Liquid input variables. Use simple `KEY=value` lines. Blank lines are ignored, and `#` begins a comment even when it appears after a value. These files are not a full shell parser: do not rely on shell expansion, `export`, or complex quoting.

```dotenv
API_BASE_URI=https://api.example.com
API_TOKEN=secret
```

Reference these values through the Liquid `env` object:

```yaml
options:
  base_uri: "{{ env.API_BASE_URI }}"
test:
  route: /users
  headers:
    Authorization: "Bearer {{ env.API_TOKEN }}"
```

Environment values and config options flow into descendant directories. Prefer one config and one environment file at the relevant project or directory level. Do not depend on iteration order between multiple config files in the same directory.

`--run` filters which specs execute; ancestor config and environment context is still discovered and applied.

## Test Spec Shape

A spec file contains a descriptor tree. A descriptor can define a test, nested descriptors, or both.

Descriptor fields:

```yaml
name: "Display name"
description: "Optional longer explanation"
tags:
  - smoke
  - api
options:
  base_uri: "https://api.example.com"
  debug: true
  retries: 1
  reports:
    - console
  skip: true
describe:
  - name: "Nested section"
    test:
      route: /health
test:
  route: /status
```

Nested `describe` blocks are traversed depth-first in source order. A section is reported immediately before its own tests. Options on a descriptor are inherited by its descendants, while options on sibling branches do not leak into one another.

`tags` is currently metadata only. Tempest parses and Liquid-renders the field, but tags cannot select or filter tests.

Common nested example:

```yaml
name: "Example API"
options:
  base_uri: "https://api.example.com"

describe:
  - name: "Users"
    describe:
      - name: "Get user"
        test:
          route: /users/1
          assert:
            - status == 200
            - body.json().id == 1
```

## Run Options and Retries

Options can appear in `.config.yml` files or under `options:` on any descriptor.

```yaml
base_uri: "https://api.example.com"
debug: false
retries: 1
reports:
  - console
  - json
concurrent: true
```

Option behavior:

- `base_uri` is prepended to a route that does not start with `http://` or `https://`. Slashes at the join are normalized.
- `debug` enables detailed request/response data.
- `retries` is the number of additional attempts allowed after assertion failure. A value of `1` permits at most two total attempts.
- `reports` selects report templates by name.
- `concurrent` enables concurrent spec-file execution when set in the root project config. Tests within each file, including retries and variable assignment, remain sequential.
- `skip` option will cause the test to be skipped and any inherited tests to be skipped. A skipped test does not run, assert or set variables.
- The CLI starts with `reports: ["console"]`, `debug: false`, `retries: 0`, and serial spec-file execution.
- When a config or descriptor specifies `reports`, it replaces the inherited list. Include `console` explicitly if console output should remain enabled.
- Options cascade from CLI defaults through parent-directory configs and ancestor descriptors. The more local configured value wins.

`concurrent` is a suite scheduler setting rather than a descriptor behavior, so set it only in the root project config. With `concurrent: true` and no `--workers` argument, Tempest uses `std::thread::available_parallelism()` as the worker limit. An explicit `--workers N` takes precedence and also enables concurrency even when `concurrent` is absent or false.

A test that fails and later passes during its retries is `flaky`. Each attempt is reported, but the final summary counts the descriptor once. The saved-variable context is restored before each retry, so values assigned by a failed attempt do not leak into the next attempt.

The zero-based Liquid input variable `retry_attempts` is available while rendering a retried test:

```yaml
options:
  retries: 1
test:
  route: "/status/{% if retry_attempts == 0 %}500{% else %}200{% endif %}"
  assert:
    - status == 200
```

## HTTP Test Fields

Supported fields inside `test:` are:

```yaml
test:
  route: /posts/1
  verb: GET
  body: '{"title": "Hello"}'
  headers:
    Content-Type: application/json
    Accept: application/json
  assert:
    - status == 200
  vars:
    post_id: body.json().id
```

HTTP behavior:

- `route` is required.
- `verb` defaults to `GET` and is case-insensitive.
- Supported verbs are `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, and `HEAD`.
- `body` is sent for `POST`, `PUT`, and `PATCH`.
- `headers` maps request header names to string values.
- Query strings must currently be written directly in `route`, such as `/comments?postId=1`.
- A `query` field exists in the Rust model but is not implemented by the HTTP runner. Do not generate examples that rely on `query:`.
- HTTP transport errors produce an empty response with status `504` and the error text in `status_message`.

An HTTP status does not fail a test by itself. Tests pass or fail according to their CEL assertions; a test with no assertions is considered passed.

## Liquid Input Interpolation

Before a request is sent, Tempest renders spec strings with Liquid. This includes descriptor metadata, `base_uri`, and test fields such as `route`, `verb`, `body`, `headers`, `assert`, and `vars`.

Useful Liquid input globals:

- `env`: values loaded from discovered `.env` files.
- `vars`: values saved by earlier tests in the same spec file.
- `retry_attempts`: zero-based attempt number; `0` is the initial attempt.
- `file_name`: the current spec-file path as a string.

Liquid input interpolation and Liquid report rendering use the same Liquid engine, but they run with different globals.

When interpolating a string into a CEL assertion, include CEL string quotes around the rendered value:

```yaml
assert:
  - '"{{ vars.expected_name }}" == "octocat"'
```

Numeric and boolean values can normally be interpolated without quotes:

```yaml
assert:
  - 'status == {{ vars.expected_status }}'
```

## CEL Assertions

Each item under `assert:` is a CEL expression evaluated against the HTTP response. It must return a boolean. A false result fails the assertion without an evaluation error. A parse error, execution error, or non-boolean result also fails the assertion and records an error message.

Available CEL response variables:

- `status`: HTTP status code as a CEL unsigned integer.
- `status_message`: canonical HTTP status text, or transport error text.
- `body`: response body decoded lossily as a string.
- `bytes`: raw response body bytes.
- `headers`: response-header map. Header names should normally be accessed in lowercase.
- `duration`: request duration in whole milliseconds as an unsigned integer.

Available Tempest CEL functions:

- `body.json()`: parses a string as JSON and returns CEL-compatible JSON data. It is normally called on the response body.
- `body.css(selector)`: parses an HTML string and returns matching elements. Each result contains `tag`, normalized `text`, and an `attrs` map. Invalid selectors produce evaluation errors.
- `body.xpath(expression)`: evaluates XPath against an XML string. Boolean, number, and string results become CEL scalars; node sets become lists of strings.
- `fileBytes(path)`: reads a file and returns bytes. Relative paths resolve from the current spec file's directory. Paths beginning with `/` resolve from the suite root selected by `--path`. Paths may not escape that root.
- `bytes.toBase64()`: encodes bytes as a standard Base64 string.
- `string.fromBase64()`: decodes a standard Base64 string and returns bytes. Invalid Base64 produces an evaluation error.

The old standalone `json` variable is obsolete and unavailable. Referencing it emits a warning explaining that `body.json()` must be used. Do not generate `json.id`, `json["id"]`, or similar expressions.

Examples:

```yaml
assert:
  - status == 200
  - status == 200u
  - body.contains("octocat")
  - body.json().id == 1
  - body.json()["display-name"] != ""
  - body.json()[0].id == 1
  - body.json().all(item, item.id > 0)
  - body.css("title").exists(element, element.text == "Example Domain")
  - body.css("a[href]").all(element, element.attrs.href.startsWith("https://"))
  - body.xpath("count(/slideshow/slide)") == 2.0
  - body.xpath("/slideshow/slide/title") == ["First", "Second"]
  - headers["content-type"].contains("application/json")
  - duration < 1000u
  - bytes == fileBytes("fixtures/avatar.png")
  - bytes.toBase64() == "aGVsbG8="
  - '"aGVsbG8=".fromBase64() == b"hello"'
```

Both dotted JSON field access and bracket access work. Prefer dotted access for ordinary identifier-like keys and brackets for keys containing punctuation or other characters that are not valid CEL identifiers.

`body.json()` parses when the CEL expression is evaluated. Invalid JSON causes that assertion or variable expression to error; there is no separate parsed-JSON response variable.

Normal CEL operators, string/list/map methods, macros, and literals supported by the bundled CEL interpreter can be used. Existing examples use methods and macros such as `contains`, `startsWith`, `endsWith`, `matches`, `size`, `all`, `exists`, `exists_one`, `filter`, and `map`.

## Saved Variables

Use `vars:` to save response-derived values for later tests. `vars` is a YAML mapping, and every value is a CEL expression evaluated against the current HTTP response with the same variables and functions available to assertions.

```yaml
name: "Save a user"
test:
  route: /users/1
  assert:
    - status == 200
  vars:
    user_id: body.json().id
    user_name: body.json().name
    response_type: headers["content-type"]
```

Do not use Liquid to extract the current response:

```yaml
# Incorrect: response extraction is not a Liquid expression.
vars:
  user_id: "{{ body.json().id }}"
```

Saved values are exposed to subsequent tests through the Liquid `vars` object:

```yaml
name: "Use the saved user"
test:
  route: "/users/{{ vars.user_id }}"
  headers:
    X-Expected-Name: "{{ vars.user_name }}"
  assert:
    - status == 200
    - 'body.json().name == "{{ vars.user_name }}"'
```

Variable scope and behavior:

- A saved variable is available only to later descriptors from the same spec file.
- The variable context resets when execution moves to another spec file.
- Define a producer before its consumer; do not rely on ordering across different spec files.
- CEL values are converted to JSON-compatible values before being placed in `vars`.
- If a variable expression cannot be evaluated or converted, Tempest stores `null`. A variable-assignment error does not itself fail the test.
- Failed retry attempts have their variable mutations rolled back before the next attempt.

## Reporters

Tempest includes these built-in report templates:

- `console`: default console output. It prints one line per passing test, combines nested descriptor names with ` › `, and prints only failed assertions beneath failed tests.
- `json`: appends JSON output to `./tempest-reports/report-{{start_timestamp}}.json`.

Enable reports with options:

```yaml
reports:
  - console
  - json
```

Report names come from template file names. `myreport.template.yml` is registered as lower-case `myreport` and selected with:

```yaml
reports:
  - myreport
```

Unknown report names are ignored. Avoid duplicate registered names, including built-in names: later-discovered templates replace earlier entries, and precedence depends on discovery location and order.

## Custom Report Templates

Custom reporters use Liquid, not CEL. Put a `*.template.yml` or `*.template.yaml` file in the test tree.

```yaml
title_template: |
  Running {{ test_count }} tests

section_template: |
  # {{ name }}

test_template: |
  {{ name }}: {{ status }} {{ status_message }}

summary_template: |
  Passed: {{ passed }}, Failed: {{ failed }}, Flaky: {{ flaky }}, Duration: {{ duration }}ms

error_template: |
  Template error: {{ liquid_error_message }}

debug_template: |
  DEBUG: {{ debug_message }}

file:
  dir: ./tempest-reports
  file_name: report-{{start_timestamp}}.txt
```

If `file:` is omitted, rendered output is printed to the console. If `file:` is present, output is appended to the configured file and the directory is created if necessary. Existing report files are not truncated. `start_timestamp` is a Unix timestamp available when rendering `file_name`.

Template fields may contain inline Liquid or refer to a `.liquid` file in the same directory:

```yaml
test_template: my-test-template.liquid
summary_template: my-summary-template.liquid
```

Liquid globals by event:

Title template:

- `test_count`: total number of discovered tests.

Section and test templates:

- `name`
- `title_path`: array of rendered ancestor descriptor names.
- `full_name`: the rendered ancestor names and current descriptor name joined with ` › `.
- `description`
- `passed`
- `test_count`: number of previously completed tests already counted in the run summary, represented as a string.
- `retry_count`: zero-based attempt number, represented as a string.
- `assertions`

Test templates additionally receive response fields:

- `status`
- `status_message`
- `body`
- `duration_ms`
- `headers`

Each item in `assertions` contains:

- `expr`
- `passed`
- `error`

Summary template:

- `passed`
- `failed`
- `flaky`
- `duration`: total run duration in whole milliseconds.

Error template:

- `liquid_error_message`

Debug template:

- `debug_message`: resolved route, response status, response headers, and response body emitted when debug output is enabled.

The Liquid engine includes its standard library plus Tempest filters. Tempest filters include `json`, `red`, `green`, `yellow`, `bright_red`, `bright_green`, `bright_blue`, `bright_purple`, their `on_*` background variants, `color_status`, and `color_duration`. Standard filters used by built-in templates include `round`.

The Liquid `json` filter serializes a report value and remains valid. It is unrelated to the obsolete `json` variable in CEL assertions.

## Complete Generated Example

```dotenv
# api.env
API_BASE_URI=https://jsonplaceholder.typicode.com
```

```yaml
# api.config.yml
base_uri: "{{ env.API_BASE_URI }}"
retries: 1
reports:
  - console
  - json
```

```yaml
# posts.spec.yml
name: "Posts"
describe:
  - name: "Get one post"
    test:
      route: /posts/1
      assert:
        - status == 200
        - body.json().id == 1
        - body.json().title.size() > 0
      vars:
        post_id: body.json().id
        post_title: body.json().title

  - name: "Use the saved post"
    test:
      route: "/posts/{{ vars.post_id }}"
      assert:
        - status == 200
        - 'body.json().title == "{{ vars.post_title }}"'

  - name: "Create a post"
    test:
      route: /posts
      verb: POST
      body: '{"title": "Tempest", "body": "Hello", "userId": 1}'
      headers:
        Content-Type: application/json
      assert:
        - status == 201
        - body.json().title == "Tempest"

  - name: "Filter comments"
    test:
      route: /comments?postId=1
      assert:
        - status == 200
        - body.json().all(comment, comment.postId == 1)
```

## Exit Codes

- `0`: no failed tests; flaky tests also return 0 unless `--strict` is used.
- `1`: one or more tests failed, warnings exist while `--warn-as-err` is enabled, or Tempest encounters an expected operational error such as invalid YAML or report I/O failure.
- `2`: one or more tests were flaky, none failed, and `--strict` was enabled.
- `70`: Tempest encountered an unexpected internal panic.

Warning-as-error handling takes precedence over the flaky exit code. Skipped tests do not affect the exit code.

Expected operational errors are written to stderr without a stack trace. Unexpected internal panics print a concise fatal message; set `RUST_BACKTRACE=1` to request diagnostic backtrace details.

## Current Limitations and Gotchas

- Tempest currently runs HTTP tests only.
- The `query` field is modeled but not implemented. Put query strings in `route`.
- `tags` is metadata only and cannot currently select or filter tests.
- Assertions and saved-variable expressions are CEL, not JavaScript or Liquid.
- The old CEL `json` variable is obsolete and does not work; always use `body.json()`.
- Unknown HTTP verbs return a default empty result with status `0` rather than a parse error.
- The HTTP client follows reqwest defaults, including redirect behavior.
- Request status alone does not determine success; write an assertion such as `status == 200`.
- JSON report files and other file-backed reports are appended runtime artifacts unless intentionally committed as examples.
- Repository examples call public services and require network access. The full example tree intentionally contains failing and flaky tests.

## Repository Layout for Contributors

Important source areas:

- `tempest/src/main.rs`: CLI flags, path selection, warnings, and exit codes.
- `tempest/src/discovery`: recursive discovery and YAML/environment parsing.
- `tempest/src/models`: YAML and runtime data models.
- `tempest/src/content`: response-content parsing.
- `tempest/src/pipeline/runners`: HTTP request execution.
- `tempest/src/cel`: shared CEL context and Tempest CEL functions.
- `tempest/src/pipeline/assertions`: assertion evaluation.
- `tempest/src/pipeline/variables`: saved-variable evaluation and assignment.
- `tempest/src/templating`: Liquid input engine and custom filters.
- `tempest/src/pipeline/reporting`: report events, Liquid rendering, reporters, and output sinks.
- `tempest/src/builtin_reporters`: built-in console and JSON report templates.
- `examples/tests`: executable examples of current behavior.

Common verification commands:

```bash
cd tempest
cargo test
cargo clippy --all-targets --all-features -- -D warnings
cargo run -- test --path ../examples/tests --run pass
```

When changing docs or examples, keep them aligned with the current models, runner, CEL context, and examples. Do not document planned fields as usable until the execution path implements them.
